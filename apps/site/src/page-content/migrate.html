Migration guide: Eccos Cloud to self-host

How to move a number from Eccos Cloud, the hosted version of the Eccos gateway, onto a deployment you run yourself on the Bun or Docker build. The steps below mirror what the code actually lets you do. There is no automatic export everything and move it button, and no scripted Durable Object migration: the honest path is to capture what the operator surface exposes, stand up the new deployment with your own credentials, re-point the webhook and subscriber, validate, and only then shut Cloud down. That path is what this page documents.

Read this first: what moves, and what cannot

Eccos Cloud stores data in a Cloudflare Durable Object (EccosGateway) with four tables: inbound_events, outbound_messages, deliveries, and config. The operator console reads all of it over a private RPC surface (GatewayRPC). That same surface is what you page through to take a snapshot, and it is scoped in ways that matter here:

  • getStatus() — health plus the connected WABA id, phone number id, display number, and connected-at timestamp.
  • getConfig() — filtered stored config rows, including the subscriber forwarding URL and the Meta webhook callback URL. The internal getAllConfig() method is not exposed to the operator.
  • listInbound(), listOutbound(), listDeliveries() — paginated, newest-first read of stored history. Each call returns at most 200 rows (default 50) and pages with the before cursor (id < before). listDeliveries() also filters by status, and listTemplates(limit) lists the WABA's message templates.
  • getSubscriberConfig() — the forwarding URL and a boolean hasSecret. The SUBSCRIBER_SECRET value is never returned.

These genuinely do not transfer, and no export will produce them: the Meta tokens (META_ACCESS_TOKEN, the Embedded Signup Business Integration System User token), META_APP_SECRET, META_WEBHOOK_VERIFY_TOKEN, ECCOS_API_KEY, and the SUBSCRIBER_SECRET value — none of these are ever readable through the operator surface, and the gateway never logs them either; the live Durable Object itself, its DurableObjectId, and its Alarm schedule (the retry loop / cron), which are platform state and cannot be copied; and the Embedded Signup OAuth connection, whose token is transient, is discarded after subscribing, and is not transportable to another infrastructure owner. You re-create all of these by hand in the new deployment with credentials you own.

Two more honest limitations. Message content ages out: on Cloud, inbound_events and outbound_messages are deleted after the content window (default 30 days), and terminal deliveries rows are redacted in place (payload emptied) on the same schedule. So whatever older history a snapshot could capture is already gone or payload-less. And because the gateway is a pass-through, your subscriber is the system of record: if your backend already archived the forwarded events, the migration may not need any message history at all — only the connection and subscriber configuration.

Step 1 — Capture what you can, while Cloud is still up

Before you change anything, write down what the current Cloud deployment knows. From the operator console (or the equivalent RPC calls), record:

  • the connected WABA id, phone number id, display number, and connected-at date;
  • the subscriber forwarding URL your endpoint listens on, and note that you will need to re-supply the signature secret (it is never shown);
  • any relevant config values the dashboard exposes — in particular the SUBSCRIBER_WEBHOOK_URL and the Meta webhook callback URL Cloud used;
  • if you want a record of recent history, page through listInbound, listOutbound, and listDeliveries (cursor before, up to 200 rows per call) and save the JSON/JSONL to a file. This is a snapshot of what is still within retention, not a database, and there is no built-in path to replay it into a new deployment — treat it as an archive, not a restore mechanism.

There is deliberately no “export all” button or bulk-download endpoint today. If a full long-lived archive matters, your own subscriber, not the gateway, is where it should live.

Step 2 — Deploy the self-hosted build

The Bun build is a single binary over a SQLite file; docker compose wraps it for you. From a checkout of the repo:

cp .env.example .env … then fill in the values below, and docker compose up -d.

The container serves on :3000 and keeps its database at DATABASE_PATH=/app/data/eccos.db on the eccos-data volume (see docker-compose.yml). Liveness is GET /health.

Set the same six secrets the Cloud deployment needed, but as environment variables in .env (not Cloudflare secrets): META_ACCESS_TOKEN, META_PHONE_NUMBER_ID, META_WABA_ID, META_APP_SECRET, META_WEBHOOK_VERIFY_TOKEN, and ECCOS_API_KEY. Also set SUBSCRIBER_WEBHOOK_URL and SUBSCRIBER_SECRET when you forward events. The Bun target config is validated by src/config.ts on boot, so a missing value fails fast at startup instead of later.

Step 3 — Own Meta credentials and re-establish the connection

On the self-hosted build the WABA/phone connection is configuration, not an OAuth handshake: you provide your own Meta app's credentials in .env and Eccos talks to Meta directly. Concretely:

  • Use your own Meta App and WhatsApp Business Account. Create a permanent System User token with the whatsapp_business_messaging and whatsapp_business_management permissions and put it in META_ACCESS_TOKEN, with the matching META_PHONE_NUMBER_ID and META_WABA_ID.
  • The number stays connected through Meta, the same as before: whoever owns the WhatsApp Business Account keeps it, and Meta still bills that account directly. Coexistence (the phone app continuing to answer) is unchanged.
  • The Embedded Signup /connect flow that Cloud used is a Workers-target convenience; its OAuth connection is not portable to the Bun build, which does not run /connect yet. On Bun you simply put those ids directly in the environment.

Because this is a new Meta-aware deployment, please triple-check the phone number id and WABA id against what you recorded in Step 1. A fresh META_ACCESS_TOKEN is expected and healthy — the migration deliberately does not carry the old one across.

Step 4 — Re-point the webhook and the subscriber

Two destinations need to point at the new deployment or stay intact:

  • The Meta webhook subscription → your gateway. Meta must call your self-host. Point Meta's webhook callback URL at https://<public-host>/webhooks/meta with your META_WEBHOOK_VERIFY_TOKEN, and subscribe the messages field. The Bun build needs a publicly reachable endpoint for Meta to reach (expose the port with ngrok or a Cloudflare Tunnel in development, or put it behind a real public URL in production).
  • The gateway → your subscriber. Set SUBSCRIBER_WEBHOOK_URL to your backend and SUBSCRIBER_SECRET to the shared secret the gateway signs forwarded events with (X-Eccos-Signature: sha256=…). Your receiver verifies that signature with the same secret. On the self-hosted build these are environment variables; the Cloud dashboard's settings screen and its resubscribe convenience are Workers-target features — on Bun you manage the target in .env and verify with a smoke test instead.

During the cutover there is a brief window where the two deployments could both receive events if Meta still points at the old Worker. That is fine, but do not run both payloads to your subscriber permanently — switch the webhook once and then decommission the old side (Step 6).

Step 5 — Smoke-test the self-host before trusting it

Validate every link of the chain before moving any traffic:

  • Health and config: curl http://localhost:3000/health returns {"ok":true}, and the process booted without a config error.
  • Webhook challenge: GET /webhooks/meta?hub.mode=subscribe&hub.verify_token=<token>&hub.challenge=… echoes your challenge back; a wrong token returns 403.
  • Signed inbound + signature verification: POST a statuses payload signed with X-Hub-Signature-256 (HMAC-SHA256 with META_APP_SECRET) — a valid signature returns 200, an invalid one 401.
  • Send API: POST /v1/messages with a Bearer ECCOS_API_KEY sends a message or template; without the key it returns 401. Templates list via GET /v1/templates.
  • Forwarding: confirm your subscriber receives the { events: […] } payload signed with SUBSCRIBER_SECRET.

The repo ships scripts/smoke.sh, which runs the health check, the webhook challenge (valid and invalid token), signed POSTs (valid / invalid signature / invalid JSON), and the send-API auth check end-to-end and exits non-zero on the first failure. Point it at your self-host with BASE_URL=http://localhost:3000 ./scripts/smoke.sh for the Bun build.

Step 6 — Validate end-to-end, then decommission Cloud, not before

Only shut Eccos Cloud down once the self-host is proven in production, not merely booting:

  • sending a message from your apps produces a delivered receipt back on the self-host;
  • a real inbound message from a customer arrives, is stored, and arrives at your subscriber with a valid signature;
  • retries work: with your subscriber briefly down, a forward is retried and then marked failed with the last error visible in the self-host store.

When those hold, decommissioning Cloud is reversible-in-spirit but destructive-in-fact: delete or roll back the Cloudflare gateway Worker (and its Durable Object), remove the /connect app from Meta, and revoke/rotate anything that only Cloud used. From that point the data in the old Durable Object is gone there — which is why the compile-what-you-can step and your subscriber's own archive, not the gateway, are the durable copy. See docs/deployment.md for rollback mechanics.
